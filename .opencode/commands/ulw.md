description: 深挖式完成任务。先并行捞上下文，再定方案，再并行执行，最后审查收尾
---

目标：$ARGUMENTS

按下面五个阶段做，不要跳步，也不要提前结束。

## 阶段一：并行捞上下文

一次性派出多个子代理，全部 `background: true`，不要串行等待：

- explore 查现有模式、约定、调用点、同类实现
- librarian 查外部库和官方文档的正确用法（涉及第三方时才派）
- looker 看截图和设计稿（有视觉材料且主体模型不支持视觉理解时才派，如果主模型支持视觉理解，直接用主模型的视觉理解能力）

每个子代理的 prompt 必须自包含，它看不到你的上下文。要写清：你要办什么事、拿到结果用来做什么决策、只要哪些、跳过哪些。

## 阶段二：定方案

上下文回来后，判断要不要 plan：

- 跨多文件、有先后依赖、路径不唯一：派 plan，让它出依赖表、并行分组、每任务验收标准
- 单文件或几步就能做完：自己列 3 到 6 步的短计划，直接进阶段三

架构取舍、连续两次修复失败、有安全或性能隐患，插一次 oracle 咨询，把它给的判断写进方案。

有歧义先问，不要带着模糊需求往下走。

如果这一步产出了计划文件（`plans/*.md`），用 question 问一句：要不要把这个计划设为持续 goal，由你一直跑到完成。

- 选要：调用 `goal_set`，goal 取计划里的目标概括并带上完成标准，source 填计划路径，然后继续阶段三
- 选不要：当普通任务做，做完就停

方案定下来后，用 todowrite 把任务列表落下来：每个任务一条 todo，content 写清要改什么、不许碰什么、完成的判定标准，status 初始 pending，priority 按依赖关键程度排。

## 阶段三：并行执行

按 plan 给的分组派 writer：

- 只有互不依赖、不碰同一批文件的任务才并行
- 有依赖的等前置返回再派
- 每个 writer 的 prompt 里写清：改哪些文件、不许碰哪些、成功标准是什么、必须交什么证据

全部返回后你自己核对：改动是否互相对得上，接口是否一致，有没有重复实现。不一致你自己收拾。

派 writer 之前把对应 todo 标成 in_progress。writer 返回后你核对通过就标 completed，没通过就写清卡在哪、保持 in_progress，下一轮接着做。

## 阶段四：审查

派 critic 审这轮改动或计划：

- 只处理它报的阻断项，阻断项必须修掉再往下
- 它给的非阻断意见列出来就行，不强行改
- 修完如果改动不小，再让 critic 重读磁盘审一遍

跑验证：构建、类型检查、测试、实际运行。以通过为准，不以 看起来对 为准。

## 阶段五：收尾

先按这个清单自查，再清理临时文件，然后汇报：

1. 空泛套话有没有
2. 机械三段式有没有
3. 有没有所有句子都一样长
4. 输出文件是否按项目原有目录结构放置并规范命名

收尾前确认 todowrite 里没有遗留的 in_progress 和 pending：还有就说明活没干完，要么补完，要么写进遗留清单再交付。

汇报要含：做了什么、改了哪些文件、跑了什么验证和真实结果、剩什么风险、你替用户做的决定。

## 并发上限

- 同一时刻最多 24 个子代理在跑
- 同一种 agent 同时最多 4 个。要更多就分批发，前一批回来再发下一批
- 单轮最多派 24 个，超了就排队，不要一次全塞出去
- 免费额度撞限流时先降并发，别减任务

## 不要派子代理的情况

- 单文件小改、单点问答、已知位置查一处东西
- 一句话能说清、一次工具调用能做完
- 只是为了 显得在并行 而派

派之前先想：这件事自己做是不是更快。
